AI × SSH × 承認

手綱付
リモートアクセス

何でも出来るからこそ、暴走させない。行動の履歴は、きっちり残す。 エージェントの要求は承認キューに並び、人間が通してはじめて実機へ。実行はすべて監査ログに残ります。 SSH GATE（ssh-gete）は、ローカルで完結する human-in-the-loop な SSH ゲートウェイです。

なぜ必要か

便利と事故は、紙一重。

一般的な MCP の SSH サーバーは、エージェントの指示をそのまま実行します。 判断ミスやプロンプトインジェクションが一発で、rm -rf や systemctl stop を本番で走らせ得る構造です。 SSH GATE は、その間に「人間が見て承認する画面」を1枚はさみます。

素の SSH ツールSSH GATE
エージェントの指示即実行承認キューに保留
Low リスクのコマンド自動で実行それでも承認必須
誰が・何を・なぜ残りにくい全件 SQLite に記録
信頼できるエージェント—承認省略を段階的に付与
通信範囲—既定 127.0.0.1 のみ

判断と実行の引き金は、人間（または人間が事前に信頼を与えたエージェント）の手に残す。それだけのことを、確実に。

機能

承認コンソールに必要なもの、ぜんぶ。

  • 1

    人間承認ゲートウェイ

    エージェントの要求は承認キューへ。GUI で内容を確認し、必要ならコマンドを微修正してから実行できます。

  • 2

    MCP サーバー内蔵

    JSON-RPC 2.0 over HTTP で list_hosts / execute_command / get_request_status などと、AI 専用セッションのツール（open_session ほか）を提供。Claude などの MCP クライアントから接続できます。

  • 3

    リスク分類

    コマンドを High / Medium / Low に推定して表示。人間の判断を助けます（あくまで目安。実行可否は承認とポリシーが決めます）。

  • 4

    監査ログ

    すべての要求・実行結果・所要時間を SQLite に記録。接続先を消しても履歴は残します。

  • 5

    ライブターミナル（SSH / シリアル）

    承認フローとは別に、人間が直接操作する対話端末を内蔵。SSH の対話シェルとシリアルポートを同じ画面で扱え、1つの接続先にタブをいくつでも開けます。

  • 6

    ローカル完結 & 最小保持

    既定の待受は 127.0.0.1:8787。パスワードは OS のキーチェーンに置き、SSH 鍵パスフレーズは既定で保存せずメモリのみ。任意で Bearer 認証も。

仕組み

エージェントと実機の間に、門番を置く。

人間が操作する GUI、状態を所有する Go バックエンド、機械が話す MCP。承認関門はその真ん中にあります。要求から実行までは、こう流れます。

  1. エージェントが要求する — execute_command でホスト・コマンド・理由を申請。
  2. 承認キューにためる — 実行せず保留し、リスクを付けて GUI に表示。
  3. 人間が承認する — 内容を確認し、必要なら微修正して「承認して実行」。
  4. 実行して記録する — SSH 実行。結果と所要時間を監査ログに残す。

ターミナル

SSH も シリアルも、ひとつの画面で。

承認フローに乗らない「人間の直接操作」も用意しています。接続先に種別（SSH / シリアル）を持たせ、ターミナルはそれに従属。 ネットワーク機器のコンソールや USB シリアルも、SSH の対話シェルと同じ操作で開けます。 ツールバーからは、Ctrl-C などの制御文字、SSH の signal（TERM・KILL・HUP・INT）、シリアルの BREAK を送れます。 シリアル接続先は MCP からは実行できません（対話 GUI 専用）。

安全設計

安全は、1個ではなく層で積む。

  • ✓

    デフォルト承認必須

    Low リスクでも自動実行しない。AutoExecuteLowRisk はバックエンドとフロントの二重で false に固定。

  • ✓

    エージェント名の必須化と専用トークン

    誰の要求かを必ず記録。承認省略は、人が付与したエージェントが、そのエージェント専用のトークンで呼んだときにしか効きません。

  • ✓

    出力上限とタイムアウト

    stdout/stderr を上限で打ち切り、接続・コマンドにタイムアウト。超過時は確実に kill。

  • ✓

    資格情報の最小保持

    パスワードは OS のキーチェーンへ（DB に平文で置かない）。SSH 鍵パスフレーズは既定でメモリのみ。トークンはマスク表示で平文を返さず、エージェント専用トークンはハッシュだけを保存。

v1 の変更

安全の層を、もう一段厚く。

v1 で加わった主な変更です。「新機能」は新しくできるようになったこと、「安全」は承認と実行の守りを固めたものです。

新機能使い方が広がる

  • +

    --headless と Web 管理画面

    --headless で起動すると、ウィンドウを出さずに MCP サーバーと Web 管理画面だけが動きます。承認・接続先の編集・ターミナル・設定は、ブラウザから操作します（Linux / macOS / Windows）。Web 管理画面は既定で 127.0.0.1:8788 に待ち受け、127.0.0.1 から開くときもログイン（管理トークン、または任意で設定する管理パスワード）が必須です。管理の資格情報は MCP の Bearer トークンとは別物で、互いに通りません。LAN に公開するには TLS が必須で、無ければ起動を拒否します。Linux 版は headless 専用ビルド（cgo なしの単体の実行ファイルで、GTK / WebKit は不要）で、systemd の unit と Docker の例も用意しています。

  • +

    AI 専用の継続 SSH セッション

    MCP の open_session / send_line / read_output / close_session で AI 専用のシェルを開き、cd や環境変数を持ち越したまま、コマンドを順に送れます。送る1行ごとにリスク判定と承認を通し（承認省略の規則も同じ）、承認されていない行はシェルに届きません。人のターミナルタブとは分けてあり、AI から人のタブを読んだり入力したりはできません。送った行と出力は監査に残ります。アイドル（既定 10 分）と最大寿命（既定 1 時間）で自動的に閉じ、人は画面から一覧・閲覧・強制終了ができます。既定はオフで、使えるのはエージェント専用トークンで認証したエージェントだけです。

  • +

    ターミナルのシグナル送信

    ターミナルのツールバーのメニューから、Ctrl-C・Ctrl-Z・Ctrl-\・Ctrl-D の制御文字と、SSH の signal（TERM・KILL・HUP・INT）を送れます。サーバーが signal に対応していなければ、その旨を表示します。KILL と TERM は確認してから送ります。シリアルでは BREAK を送れます。

  • +

    複数タブ、サーバータブ、ショートカット

    1つの接続先に、シェルをいくつでも開けます。タブは画面を移っても閉じず、1つ閉じても他のタブはそのまま。画面の上には接続先ごとのタブがあり、承認キューや履歴をその接続先で絞り込めます。サイドバーには、接続中のセッション、シェルの数、実行中のコマンド数、MCP の待受状態と承認待ちの件数を表示します。新しいシェル・タブを閉じる・タブやサーバーの切り替えには、キーボードショートカットがあります（macOS は Cmd、Windows は Ctrl+Shift、Web 管理画面では Alt+Shift）。

  • +

    パスワードは OS のキーチェーンへ

    接続先のパスワードは SQLite ではなく、OS のキーチェーン（macOS のキーチェーン、Windows の資格情報マネージャー、Linux の Secret Service）に保存します。キーチェーンが使えないときも、平文で DB に書くことはしません（そのセッションの間だけ使うことはできます）。DB に残っていた平文のパスワードは、起動時にキーチェーンへ移します。SSH 鍵のパスフレーズは既定では保存せず、入力するときに「キーチェーンに保存する」を選んだときだけ保存します。headless では保存先を keychain / file（0600 の secrets.json）/ env から選べます。

  • +

    接続先の管理と編集画面

    接続先は名前ではなく不変の ID で管理するため、名前を変えても履歴やタブがついてきます。パスワードは保存後に画面へ返しません（空欄のまま保存すれば、保存済みの値を保ちます）。「接続テスト」は保存前の入力でも試せて、保存済みの状態は書き換えません。編集画面には「保存済み／未保存の変更あり」を表示し、未保存のまま移ろうとすると確認します。

  • +

    MCP：結果の取得・再送・終了コード

    get_request_status で、承認キューに入った要求の状態と結果を取得できます（wait_seconds で最大 60 秒待てます）。client_request_id を付ければ、24 時間以内の再送は新しく実行せず、同じ request_id を返します。結果には exit_code が入り、失敗は isError で判定できます。

安全承認と実行の守りを固める

  • ✓

    ブラウザ経由の攻撃を遮断

    悪意ある Web ページから localhost の MCP へ要求を送り込む経路を塞ぎます。Origin ヘッダ付きの要求は既定で拒否（403）、Host はポート番号まで照合（DNS rebinding 対策）、POST は application/json 以外を拒否。127.0.0.1 以外で待ち受けるには Bearer 認証が必須です。

  • ✓

    承認省略は専用トークンだけ、High は必ずキューへ

    エージェント名を名乗るだけでも、共有の Bearer トークンでも、承認省略は使えません。効くのは、そのエージェント専用のトークン（発行時に一度だけ表示し、保存するのはハッシュだけ）で MCP を呼んだときだけです。承認省略には期限（承認画面から付けたときは 8 時間）、上限のリスク（Low か Medium）、対象の接続先を持たせられ、High リスクは常に承認キューに入ります。既定では、sudo を含むコマンド、本番タグ（prod など）の接続先、Low 以外のコマンドも承認が必要です。

  • ✓

    リスク判定は許可リスト方式

    Low になるのは、許可リストにある読み取り専用のコマンドを素の引数で呼んだときだけです。クォート、エスケープ、変数の展開、リダイレクト、制御文字や見えない文字、インタプリタに渡すコードなど、読み切れない書き方は High にします。;・&&・| でつないだコマンドは1つずつ判定し、いちばん高いリスクを採ります。許可リストにも危険なコマンドの一覧にも無いものは Medium です。

  • ✓

    ホスト鍵の検証（TOFU）

    初めて接続するホストの鍵は、人が画面から接続テストをしたときに ssh-gete 専用の known_hosts（0600）へ記録し、指紋を表示します。エージェント（MCP）からは、記録の無いホストに接続しません。鍵が記録と違えば、どの経路でも接続を拒否します。厳格モードでは ~/.ssh/known_hosts も信頼し、新しい鍵は記録しません。

  • ✓

    実行先が変わったら承認を止める

    要求のあとで接続先の user@host:port が変わっていたら、承認しても実行しません。エージェントには、もう一度要求してもらいます。どの承認の経路でも同じです。

  • ✓

    承認しても、実行は1回だけ

    承認・拒否は DB の compare-and-swap で状態を進めます。ボタンの二重クリックや「承認」と「拒否」が競合しても、実行は1回だけ。実行中にアプリが終了した要求は、次の起動時に「中断」として記録され、もう一度承認することはできません。

  • ✓

    承認時の修正と、その記録

    承認画面でコマンドを直してから実行できます。直したコマンドはリスクを判定し直し、上がった場合はもう一度確認を求めます。要求されたコマンドと実際に実行したコマンドは、別々に履歴へ残ります。

  • ✓

    監査 API の保護

    監査用のエンドポイント /audit/events は GET だけを受け付け、Bearer 認証が有効なときはトークンが必要です。返す件数にも上限（既定 100 件、最大 500 件）を設けました。

  • ✓

    CI と依存関係

    テストは macOS・Windows・Linux の3つの OS で -race 付きで実行し、govulncheck と npm audit（high 以上で失敗）も毎回かけます。GitHub Actions は commit SHA で固定し、更新は Dependabot で追います。リリース用のワークフローは、成果物に SHA256SUMS.txt を添付します。

FAQ

よくある質問

もっと詳しい紹介・背景は？
開発の背景や使いどころを Qiita の紹介記事にまとめています → SSH GATE 紹介記事（Qiita）。
※ 限定共有リンクです。
本当にエージェントから勝手に実行されませんか？
はい。MCP 経由のコマンドは、既定ではリスクに関係なく承認キューに入ります。キューを通らずに実行されるのは、人が特定のエージェントに「承認省略」を与え、そのエージェントが専用のトークンで呼んだときだけです。承認省略には期限と上限のリスクがあり、High リスクのコマンドは承認省略があっても必ず承認キューに入ります。AI 専用セッションで送る1行ずつも、同じ規則で承認を通ります。
リスク分類（High/Medium/Low）はどこまで信用できますか？
Low になるのは、許可リストにある読み取り専用のコマンドを素の引数で呼んだときだけで、読み切れない書き方は High にします。それでも判定はコマンドの文字列だけを見るので、接続先で同じ名前のコマンドが実際に何をするかまでは分かりません。あくまで人間の判断を助ける目安で、これ自体が実行可否を決めるわけではありません。実行可否は承認とポリシーが決めます。
外部に公開されますか？
既定の待受は、MCP が 127.0.0.1:8787、headless の Web 管理画面が 127.0.0.1:8788 で、同じ PC からだけ使う前提です。Origin ヘッダ付きの要求は既定で拒否します。LAN に公開するには、MCP は Bearer 認証が、Web 管理画面は TLS が必須で、満たさないと待ち受けません。Web 管理画面は、どこから開いてもログインが必要です。
シリアルポートにも使えますか？
使えます。接続先の種別を「シリアル」にすると、ターミナル画面でシリアルコンソールが開きます。SSH と同じ操作感です。なお、シリアルは対話 GUI 専用で、MCP（エージェント）からは実行できません。
資格情報はどこに保存されますか？
接続先のパスワードは OS のキーチェーンに保存し、SQLite には残しません（headless では file や env も選べます）。SSH 鍵のパスフレーズは既定では保存せず、アプリ起動中のメモリにだけ持ちます（保存を選んだときだけキーチェーンへ）。SQLite には接続先の設定や鍵のパス、共有の Bearer トークンが入り、DB ファイルは 0600 で作ります。エージェント専用トークンは、ハッシュだけを保存します。保存したパスワードは画面に返しません。
保証はありますか？
